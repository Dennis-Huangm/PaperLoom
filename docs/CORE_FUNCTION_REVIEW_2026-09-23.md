## Standards：实现与数据契约

### S1 · P1：Obsidian 重同步会删除托管区块前的个人内容

位置：`src/arxiv_ra/obsidian.py:758-770`。

已有文件包含托管标记时，只保留结束标记之后的文本，再用新 frontmatter 和正文重建文件。用户写在开始标记之前的笔记会消失，用户自行添加的 frontmatter 字段也没有被合并保留。这违背 README 对“保留区块外的个人笔记”的承诺。

离线复现：在开始标记前加入 `USER_PREFIX`，再次同步后该文本消失。现有测试只覆盖尾部备注。

建议：只替换托管标记之间的正文；区分应用拥有的 frontmatter 字段和用户字段；首次修复及迁移时保留备份。增加前部、尾部、自定义字段、损坏标记四类测试。

### S2 · P1：当前方向的 Obsidian 全量同步会导入其他方向报告并覆盖周报

位置：`src/arxiv_ra/obsidian.py:118-144`、`:299-309`。

`sync_all()` 扫描全部报告与周报，不检查 metadata 的 `profile_id`；`sync_weekly()` 又以当前方向命名目标文件。同一周多个方向的源文件会写向当前方向的同一周报。

离线复现：A/B 同周周报分别包含 `CONTENT_a` 和 `CONTENT_b`，执行 A 的同步后，A 目录中的周报最终含 `CONTENT_b`。

建议：按源产物方向过滤，明确旧版无方向数据的兼容策略；周报 manifest 使用方向和周次组成的键。

### S3 · P1：同一论文在不同方向的 Obsidian 笔记相互覆盖

位置：`src/arxiv_ra/obsidian.py:826-834`、`:532-539`。

笔记查找与 manifest 只以基础 arXiv ID 为键。虽然新路径包含方向名，后续同步先命中旧 manifest，因此 B 方向会复用 A 的文件并改写方向、状态和标签。此问题在直接反馈同步时也存在，单独修复 S2 不够。

离线复现：A/B 对同一论文调用同步，返回同一路径，A 文件的 profile 被改为 B。

建议：方向化笔记使用 `(profile_id, arxiv_id)` 标识；版本化报告和附件加入 revision。若未来要提供跨方向共享笔记，需显式存储各方向独立的状态，而不能用最后一次同步覆盖。

### S4 · P2：点击报告的 Zotero 按钮可能保存另一份报告

位置：`src/arxiv_ra/templates/reports.html:38`、`src/arxiv_ra/web.py:735-736`。

列表按钮只提交基础 arXiv ID，服务端在全部报告中取首个同 ID 条目。用户点击旧版或另一方向的报告时，导出的可能是日期更新的另一份报告。结论来自模板到路由的完整数据流静态检查。

建议：按钮提交稳定产物标识，在输出目录内解析并验证，然后导出用户选定的那份报告；提交时捕获方向、版本和路径。

### S5 · P2：Zotero 的 PDF 缓存没有按版本区分

位置：`src/arxiv_ra/web.py:226-251`。

缓存路径是 `zotero-cache/<基础ID>.pdf`，文件非空即复用。先保存 v1、后保存 v2 时，仍会返回 v1 的 PDF。相同 ID 并发下载还共用一个 `.part` 路径。结论来自缓存命中与下载路径静态检查。

建议：缓存按确定的修订版命名，下载使用唯一临时文件和原子发布；附件名称包含版本；重复操作保持幂等。

Standards 共 5 项，其中最高风险是 S1 的个人笔记丢失，以及 S2/S3 的跨方向覆盖。共同改进点是统一产物身份，避免各模块独立使用基础 ID 或文件名猜测目标。

## Spec：功能承诺与实际行为

### F1 · P2：摘要级回退缓存会阻止模型恢复后的重新生成

位置：`src/arxiv_ra/abstracts.py:89-98`、`:189-195`。

首次生成未配置模型或模型暂时失败时，回退文本同样进入持久缓存。后续缓存命中只检查签名和字段是否非空，不检查 `source=fallback`；签名也不含模型配置。恢复服务或更换模型后，普通生成仍复用原回退结果。

纯内存 mock 复现：首次模型超时，服务恢复后再次生成，模型总调用次数仍为 1，缓存仍为 fallback。建议：缓存区分模型成功、抽取回退、临时失败；对回退设置重试策略，在明确写入任务中允许重新生成；提供“重新生成摘要/推荐理由”入口。页面 GET 继续只读本地缓存，避免打开页面触发模型费用。

### F2 · P2：摘要与周报可能混用其他方向、其他修订版的报告

位置：`src/arxiv_ra/abstracts.py:38-57`、`src/arxiv_ra/weekly.py:121-127`。

两个读取入口都只按基础 arXiv ID glob 文件，并按路径排序选报告，没有核对方向和论文版本。历史 v1 推荐可能获得 v2 的结论或其他方向的“为什么值得阅读”；周报中展示的论文快照与实际给模型的报告证据也可能不一致。路径的字符串顺序也不是可靠的版本先后顺序。

纯内存 mock 复现：方向 a 的 v2 论文读取到方向 z 的 v9 报告。建议：复用带方向、版本约束的产物查询接口；精确版本缺失时保留摘要级材料或明确显示证据版本，不能静默借用另一版本。

### F3 · P1：同一天再次推荐会替换当天历史，先前推荐从回顾中消失

位置：`src/arxiv_ra/pipeline.py:272-278`、`:292-294`；消费端 `src/arxiv_ra/weekly.py:105-113`。

当天第一次推荐 A，第二次正常刷新时 A 已在去重状态中，若选到 B，则当天推荐文件直接写成 B。A 仍在 processed 中，却不再出现在当天历史；周报也只看到最后一次落盘的推荐。单独的发现 manifest 不等于保留带完整内容的已发布推荐快照。

纯内存 mock 复现：当天推荐只剩 B，processed 却为 A+B。建议：明确“当天累计”与“本次推荐”的区别。优先保存不可变 run-id 快照，再维护每日聚合视图，去重以 ID/版本的明确规则执行；周报按已发布记录汇总。若产品决定历史只展示末次结果，需在界面明确告知并提供此前批次入口。

Spec 共 3 项，其中 F3 是 P1 的历史记录丢失；F2 还会影响研究结论与原始证据的一致性。

## 版本追踪专项

### V1 · P1：追踪对象漏掉收藏论文，却包含“不相关”论文

位置：`src/arxiv_ra/version_tracker.py:53-59`；`src/arxiv_ra/feedback.py:14-16`。

当前反馈仅有 `not_relevant`，收藏存在另一 collection。Tracker 使用 FeedbackStore，不使用 PaperLibraryStore。只收藏、没生成报告且不在 Zotero 中的论文不会被追踪，明确不相关的论文却会占用追踪额度。

离线复现已确认。建议默认来源为收藏、当前方向报告和显式关注清单；是否追踪已排除论文应是明确选择，不能把“反馈”统一当作关注。

### V2 · P2：报告来源未按方向过滤

位置：`src/arxiv_ra/version_tracker.py:53-56`。

状态文件按方向保存，但报告扫描跨全部方向。离线复现：只有 B 的报告，也出现在 A 的追踪结果。建议检查 `metadata.profile_id`，并定义遗留无方向报告的归属策略。

### V3 · P2：一篇论文的 PDF 对比失败会中断整批版本检查

位置：`src/arxiv_ra/version_tracker.py:112-119`、`:146-152`。

新版本事件要等 PDF 下载、解析和报告生成完成后才加入状态；下载和解析不在局部异常处理内。任意一篇失败，循环退出，最后统一落盘也未执行。此前已查询到的最新版本和新事件没有保存。

离线注入 PDF 下载失败，确认整个检查抛错且版本状态保持旧值。建议先保存“检测到新版”，再独立执行差异分析；逐篇记录失败并可重试，不阻塞其他论文。差异失败不能等同于“没有新版本”。

### V4 · P2：固定截取前 50 篇，没有轮询或待检查提示

位置：`src/arxiv_ra/version_tracker.py:79`；`src/arxiv_ra/config.py:153` 附近。

默认 `max_tracked=50`，每次只取来源插入顺序的前缀，未按最近检查时间轮换。来源集合及枚举顺序稳定时，后续论文会一直被排除；界面没有显示“另有多少篇未检查”。离线验证重复调用返回同一前缀。

建议将“每批检查数量”与“关注总量”分开，使用检查时间/用户优先级轮询，显示本轮覆盖量与待检查量。

版本专项共 4 项，最影响预期使用的是 V1；上述问题应与新增同步能力一并规划。

## 用户提出的“主动同步到最新版”：建议作为下一项主要功能

现状确认：版本页只有“立即检查”和“查看差异”；Tracker 更新的是 `latest_version` 和差异产物，没有更新收藏快照、生成新版阅读报告、更新 Zotero 或同步 Obsidian 的流程。CLI `report <无版本ID>` 已可查询最新并生成新报告，但这是手动替代步骤，不是版本更新闭环。

### 产品行为

每篇论文同时显示：**本地版本 / arXiv 最新版本 / 阅读报告版本 / Zotero 与 Obsidian 同步状态**。首次检查即使只是建立服务器基线，也要根据本地已有版本提示是否落后；当前“首次不生成更新事件”是文档化行为，本身不是实现错误，但不足以表达本地状态。

提供三个操作：

1. **同步最新版**：下载并保存最新元数据/PDF，更新当前文献库引用，保留原版本。
2. **同步并重建报告**：在上述操作后生成新版报告，并清楚标注全文成功、摘要回退或生成失败。
3. **批量更新已关注论文**：可勾选论文及目标集成，展示待处理数、预计模型调用范围，支持失败重试。

自动模式分级：只通知、自动下载、下载并生成报告。方向或论文级可设置；主动同步先提供手动入口，自动策略在错误恢复可靠后启用。

### 实现约束

- 检查发现 v3 后，把该次任务固定到 v3。执行中出现 v4 可作为下一次更新，避免多个步骤下载不同修订版。
- 区分远端最新版本、已下载版本、报告版本、每个外部目标同步版本；一个 `latest_version` 无法表达部分成功。
- 建议任务步骤：发现 → 获取指定版本 → 发布本地产物 → 更新当前收藏引用 → 可选生成报告 → 各集成独立同步。
- 历史推荐快照保持原版本，这与 CONTEXT.md 一致。收藏的“当前版本”可前进，同时保留最初收藏时间和原始来源。
- 失败保留旧产物，记录失败步骤，仅重试未完成部分；网络失败使用旧缓存时绝不能宣称“已更新到最新版”。
- 同一方向/论文/目标版本重复执行应幂等；本地文件先写临时目录再发布；集成失败不撤销已经成功下载的文件。
- Zotero 已有条目目前主要是去重和补附件（`zotero.py:124-132`），真正的更新还需要明确哪些字段由应用管理、怎样保留人工编辑、PDF 保留旧版还是新增附件。
- Obsidian 同步必须先修复 S1-S3，再用于自动批量更新。

验收场景：本地 v1/远端 v3；首次检查本地落后；本地已是最新；PDF 失败；模型失败；Zotero 离线；更新中切换方向；同论文不同方向；重复点击；用户固定阅读 v1；部分成功后重试；超过每批数量的轮询。

2. **版本更新闭环**：修正关注来源、逐篇失败隔离和轮询，增加本地/远端版本状态、单篇及批量同步，再接集成。
3. **恢复与可追踪性**：回退内容补生成、不可变推荐批次、持久任务与分步骤重试。
4. **研究效率**：阅读进度、可解释推荐、带证据的跨论文比较与搜索。

不需要先重写整个项目。已有 `PaperResolver`、方向化存储、阅读状态锁、后台任务上下文与集成适配器可以复用。优先抽出带方向/修订版约束的产物查询接口，让摘要、周报、版本追踪和导出使用同一套选择规则。
