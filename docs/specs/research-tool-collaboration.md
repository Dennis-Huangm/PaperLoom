# PaperLoom、Zotero 与 Obsidian 协同：收录、跳转与可靠同步

## Problem Statement

用户在 PaperLoom 发现和筛选论文，在 Zotero 管理 PDF，在 Obsidian 整理研究理解。应用已经支持 Zotero 论文与附件保存、Obsidian 推荐和报告导出，以及指定版本的分步同步；但日常保存缺少统一持久的跨应用关联，用户难以从论文直接打开对应条目或笔记，也难以判断哪些材料已经成功保存、失败后应该重试什么。

普通保存返回的 Zotero 条目身份与 Obsidian 的笔记清单没有贯通。现有 Zotero 查重请求的某些失败会被视为空结果，存在随后创建重复条目的风险。已有版本同步的状态与重试能力应复用，而不是让普通导出继续形成另一套不可追踪的操作。

## Solution

优先完成“选定论文 → 收录到所选工具 → 看到各目标回执 → 打开对应资料”的闭环，再补齐部分失败、重试和历史关联修复。保留原有单目标保存入口，并增加可分别选择 Zotero、Obsidian 的收录操作。沿用现有分类、专用目录、笔记命名及手写内容保护规则。

PaperLoom 负责发现、筛选及生成阅读辅助材料，Zotero 负责文献、PDF 与批注，Obsidian 负责个人理解、跨论文关联及写作。首版不导入批注或个人笔记，不进行双向编辑同步。应用已有的个人笔记功能继续可用。

## User Stories

1. 作为研究者，我希望从推荐中的论文发起收录，以便减少重复寻找论文的操作。
2. 作为研究者，我希望从已收藏论文发起同样的收录，以便使用一致的工作流。
3. 作为研究者，我希望保存选定的历史报告，以便保留我实际阅读过的材料。
4. 作为研究者，我希望分别选择 Zotero 和 Obsidian，以便只使用已经配置的工具。
5. 作为研究者，我希望现有保存按钮继续可用，以便保留熟悉的操作习惯。
6. 作为研究者，我希望收录前知道将处理哪些 PDF、报告和版本，以便避免导出错误材料。
7. 作为研究者，我希望收录不自动改变收藏或不相关标记，以便维持研究方向内的阅读状态。
8. 作为研究者，我希望可靠匹配到已有 Zotero 条目，以便避免重复建库。
9. 作为研究者，我希望多个可能的匹配被明确提示，以便不把资料连到错误条目。
10. 作为研究者，我希望同一论文在不同研究方向复用 Zotero 条目，以便统一管理文献。
11. 作为研究者，我希望不同研究方向的笔记与阅读状态继续独立，以便区分不同研究问题。
12. 作为研究者，我希望在论文旁打开对应 Zotero 条目，以便继续阅读 PDF。
13. 作为研究者，我希望在论文旁打开对应 Obsidian 笔记，以便记录自己的理解。
14. 作为研究者，我希望 Obsidian 论文笔记包含已关联 Zotero 条目的入口，以便从理解笔记回到文献。
15. 作为研究者，我希望每个工具分别显示处理结果，以便知道一边成功、一边失败的情况。
16. 作为研究者，我希望看到已同步的版本与报告，以便区分旧成果和待更新材料。
17. 作为研究者，我希望应用重启后仍保留关联和回执，以便不依赖短暂的成功提示。
18. 作为研究者，我希望重试未完成部分，以便不重复创建已经保存的条目和附件。
19. 作为研究者，我希望连续点击或重复执行同一收录不会生成重复资料，以便安心恢复操作。
20. 作为研究者，我希望 Zotero 未启动或授权失效时得到可执行的提示，以便恢复后继续。
21. 作为研究者，我希望批量收录保留逐篇结果，以便单独处理失败论文。
22. 作为研究者，我希望 Obsidian 手写内容和自定义属性继续保留，以便不丢失研究思考。
23. 作为研究者，我希望损坏的托管标记导致明确停止写入，以便先修复笔记结构。
24. 作为研究者，我希望笔记移动或条目删除后显示需要修复关联，以便不被旧成功状态误导。
25. 作为研究者，我希望更换 vault 或 Zotero 目标后旧关联不被误用，以便隔离不同资料库。
26. 作为研究者，我希望同步新修订版时保留旧版附件和历史推荐，以便追溯此前的阅读依据。
27. 作为研究者，我希望已有导出成果可以建立关联，以便不必迁移整个知识库或重新复制所有文件。
28. 作为研究者，我希望未连接的目标不会妨碍另一个目标收录，以便逐步配置协同工具。

## Implementation Decisions

- 入口范围为推荐论文、收藏库论文、报告列表及现有版本同步。沿用现有配置开关和附件选择，不默认扩大自动导出范围，不要求安装新的 Zotero 或 Obsidian 插件。
- 增加一个共享的收录协调层，普通保存、批量保存和版本同步通过它维护关联与回执；沿用现有 Zotero、Obsidian 适配器及任务执行设施。避免另建后台常驻队列或独立调度器。
- 关联与回执是不同记录：关联保存外部资料身份，回执保存某次目标操作、明确版本及所选材料的结果。保存操作标识、目标配置身份、论文身份、研究方向、请求材料、各步骤结果、外部身份、时间及可展示的失败原因，不存授权密钥。
- 论文使用规范化 arXiv 基础身份；指定版本与报告身份单独保存。Zotero 关联包含目标文献库身份和条目 key，不能仅用条目 key 或分类名称；Obsidian 关联包含 vault 身份、研究方向和 vault 内相对路径。相同 Zotero 文献库内调整分类不会创造新的论文身份。不得因标题变化或研究方向显示名变化丢失既有关联。
- 优先验证已保存的外部关联，再按可靠 arXiv ID、DOI 查重。标题相似只能提示候选，不能自动认定同一论文。多个可靠标识互相冲突或匹配到多个条目时，进入需要用户选择的状态；展示候选并允许选择现有条目，不自动取最早条目。
- 查重接口的网络、授权、服务错误及不可解析响应必须作为失败传播，不能转换为空结果后继续创建。只有查重成功且无匹配才允许新建。
- 收录请求固定当前研究方向、推荐快照或报告身份、指定版本、目标及材料清单。执行中配置或页面选择变化不改变已提交任务；目标配置身份变化后，旧任务需明确按原目标重试或发起新操作。
- 首版支持导出已有材料和现有下载流程；收录本身不隐式生成新报告或升级为最新版本。目标未启用时给出配置入口，用户可取消该目标并继续其他已配置目标。
- 对论文与目标的写入进行串行化或等效去重；同一请求的重复提交复用结果。版本同步和普通导出必须共享去重边界。成功的外部创建应立即保存回执，后续附件失败不能丢失父条目身份。
- 各目标记录待处理、执行中、成功、部分成功、失败、需用户处理等结果，并保留步骤级完成情况。另行展示资料是否待更新、关联是否已验证；不能把旧版本成功或未检查的外部存在性显示成当前全部同步完成。
- 成功要求所选必需步骤均完成；未选择的材料不算失败。两边结果独立持久化。一边失败不回滚另一边，不删除外部已成功成果。批量操作返回逐篇、逐目标回执。
- 重试检查已完成的条目和材料，仅继续缺失步骤。附件创建后上传失败要记录附件身份并恢复同一附件；无法确认外部写入结果时先核对，不能盲目再次创建。用户手动删除的条目或附件不自动重建，先提示修复或重新收录。
- 进程重启后未完成的任务标为中断且可恢复，不永久停留在执行中，不自动假定成功。沿用已有持久化和原子写入方式，保留旧版本同步记录的兼容读取。
- 单篇打开入口只在已有可靠关联时提供。使用外部工具支持的 URI 打开 Zotero 条目和 Obsidian 笔记，正确编码非 ASCII 字符、空格和特殊字符；在实施时核实当前协议契约。链接启动不等同于目标存在性验证，不伪造启动成功回执。
- Obsidian 托管区可写入 Zotero 条目入口；尚未关联时不生成猜测链接。后续关联成功可更新这一托管入口，更新失败按 Obsidian 未完成步骤呈现。不向 Zotero 写入依赖本机路径的 Obsidian 反向链接。
- 保留现有 Obsidian 目录、命名、托管标记及自定义 YAML 保留规则；应用自有属性可更新，其他属性与托管区前后个人文本保持原样。托管标记损坏或路径不安全时停止该笔记写入。
- 历史 Obsidian manifest 和版本同步回执可用于惰性导入关联；导入前校验目标身份和论文身份。证据不足时显示未关联，不从“曾经执行过保存”推断成功。已有 Zotero 条目通过可靠查重关联，不批量迁移用户资料。
- 提供显式检查或修复关联操作。Obsidian 原路径失效时，仅在配置的专用目录内通过托管身份查找；唯一匹配可修复路径，多匹配须选择。Zotero 旧 key 失效时可重新匹配或选择条目。两者均不得直接重建用户已删除的资料。
- 回执存储应纳入应用现有备份范围；恢复后外部关联先标为待验证，尤其不得将另一台机器的 vault 路径直接视为可用。

## Testing Decisions

- 以可观察行为为验收依据：用户操作后出现何种状态、写出了哪些资料、再次操作是否产生重复、失败能否恢复。避免针对内部私有方法结构编写镜像测试。
- 主要测试边界沿用现有 Web 操作及版本同步服务，配合临时输出目录、临时 vault 和模拟 Zotero HTTP 响应。共享协调层通过这些入口覆盖，不为每个调用层重复同一套测试。
- 少量适配器契约测试覆盖授权失败、非成功查重响应、异常响应结构、附件分阶段上传和 URI 编码。已有 Zotero 去重测试中“仅标题匹配”和“多个候选取最旧”的预期须按新规则调整。
- 复用现有数据完整性测试对手写内容、自定义属性、损坏托管标记、历史报告选择和指定版本的保护；复用版本同步测试的分步失败与重试设施。
- 核心场景必须覆盖：双目标成功；单目标失败；批量部分失败；重启后的状态恢复；重复与并发提交；外部已成功但本地回执写入失败；父条目创建成功但附件上传失败；重试不产生重复资料。
- 身份场景必须覆盖：同论文跨研究方向、同标题不同论文、冲突的 DOI/arXiv 身份、多个匹配、切换目标库/vault、分类改名、指定历史报告及新旧修订版并存。
- 修复场景必须覆盖：笔记移动、重复托管身份、外部条目删除、历史 manifest 导入、备份恢复后的待验证状态，以及原配置变化后的重试目标确认。
- 界面验收覆盖每目标状态、材料及版本显示、错误后的下一步入口、失效关联提示、中文和特殊字符路径的单篇打开链接。持续集成不依赖用户正在运行的真实桌面程序。
- 发布前做一次受控的真实 Zotero 与 Obsidian 手动冒烟验收，验证协议跳转和一篇论文的收录、重复执行及部分失败恢复；使用专用测试资料。真实联调是补充验收，不能代替自动化用例。

## Out of Scope

- Zotero 高亮、批注及笔记导入，Obsidian 个人笔记回流，三端双向编辑、删除传播及冲突自动合并。
- 使用现有外部资料库增强推荐或模型上下文，全文索引外部 vault，以及让个人笔记参与模型调用。
- 重构现有 Obsidian 知识库结构、大规模迁移历史文件、自动合并 Zotero 重复条目、任意插件模板兼容。
- 新增 Zotero 云端或群组库支持、多用户协作、跨设备路径自动迁移及通用同步平台。
- 改变现有收藏语义、推荐快照或版本追踪策略，移除应用内阅读和个人笔记功能。

## Further Notes

- 用户已接受优先级：先收录与跳转，再同步可靠性；接受三款工具的职责分配，并优先沿用现有资料组织。详细规则据此整理为首版实施默认值，不代表已经实现。
- 实施可分两阶段交付，但完成本规格需要两阶段验收均通过：第一阶段是持久关联与单篇跳转；第二阶段是共享回执、错误传播、幂等重试及关联修复。
- 用户已确认测试边界：沿用现有 Web 操作与版本同步服务，使用临时 vault、模拟 Zotero 响应及少量适配器契约测试。
- 仓库已经启用 GitHub Issues 并提供 ready-for-agent 标签，本规格发布到该项目 Issue tracker。
