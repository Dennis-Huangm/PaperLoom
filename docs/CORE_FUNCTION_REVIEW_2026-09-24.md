## Standards：实现与数据契约

### S1 · P1：报告正文未经净化，外部文本可成为同源脚本

位置：`src/arxiv_ra/render.py:71-86,95-112`；`src/arxiv_ra/web.py:170-183`。

`markdown_with_math()` 直接使用 Markdown 转换结果。离线输入普通 `<script>` 与带 `onerror` 的图片，输出原样保留二者。生成报告通过 `/artifacts` 与管理 API 同源提供，当前响应没有限制此类正文脚本的 CSP；现有跨站检查也不隔离同源报告。模型输出或论文文本中的原始 HTML 因而可能在打开报告时执行，并访问本地应用的读写接口。这是渲染信任边界的实现问题，不是要求把应用改造成公网多用户服务。

建议：对转换后的正文与目录使用成熟的 HTML 白名单净化，限制事件属性、脚本和危险 URL；保留必要的表格、公式和图片。进一步用 CSP 或独立来源/沙箱隔离报告正文与管理功能，并整理现有内联脚本以兼容策略。

验收：脚本、事件属性与危险链接均失效，表格、KaTeX、方法图、目录仍正常。这里只验证了输出与代码路径，没有执行攻击或声称实际数据已泄露。

### S2 · P2：收藏操作丢失页面所选论文的日期和修订版

位置：`src/arxiv_ra/static/app.js:571-579`；`src/arxiv_ra/templates/reports.html:36`；`src/arxiv_ra/web.py:412-422,439-455`；`src/arxiv_ra/paper_data.py:43-66`。

报告生成和 Zotero 导出已有快照参数，但收藏入口仍只传基础 arXiv ID。后端重新扫描最新日期的推荐，不能知道用户选的是哪一条记录。

离线复现：9 月 23 日有 v1、24 日有 v2，模拟旧推荐页收藏请求，返回 200，实际保存 `version=2, source_date=2026-09-24`；从 v3 报告的收藏入口提交同一 ID，实际也可能收藏已有推荐中的 v2。跨方向报告在全局报告库可见，但收藏查询限当前方向，无匹配数据时还可能返回 404。

建议：收藏动作传递明确的 profile、origin、source_date、revision 或 report_id，由服务端校验并保存所选快照。明确“收藏此快照”与“推进收藏到最新版”的不同意图，避免再次收藏覆盖已有更新版本。

验收：同 ID 不同日期/修订版/方向均保存所选对象；已有较新收藏不能静默降级；报告列表和报告内按钮行为一致。

### S3 · P2：旧标签页提交会写入另一个研究方向

位置：`src/arxiv_ra/web.py:413-418,440-445,467-470`；设置保存见 `:677-689`。版本策略的 `:535-537` 已有类似校验，可复用。

多个写入入口只在收到请求时读取全局活动方向，没有校验页面渲染时的方向。离线复现：A 页保留，另一个标签页切到 B，再提交 A 页的收藏请求，返回 200，A 没有收藏、B 新增收藏。删除、反馈和方向检索设置也沿用同样的全局活动状态，可能误改另一方向。后台任务已经捕获“提交时配置”，但这不能识别旧页面的原始意图。

建议：方向相关表单/API 携带页面 profile_id，服务端按明确方向执行或在活动方向变化时返回 409 提示刷新。设置写入可进一步检查配置版本，避免过期表单覆盖更新配置。

验收：双标签页切换、旧页面收藏/移除/反馈/保存设置均不误写其他方向；已排队任务继续使用提交快照。

### S4 · P2：复用已成功的同步步骤后，收藏仍可停留在旧版

位置：`src/arxiv_ra/version_sync.py:110,155-159`。

`library` 步骤没有有效性检查，曾经成功就直接跳过。离线复现：收藏 v1 → 同步到 v3 → 从历史记录重新收藏 v1 → 再同步最新版；输出 `operation: succeeded saved: 1`。同步显示成功，但当前收藏未前进。README 承诺同步“推进已有收藏的当前版本”，此路径不满足。

建议：每次执行都依据当前阅读状态核对该步骤，而不只看上次成功标记；复用 `refresh_saved` 的比较更新和不降级规则。用户已取消收藏时不得自动恢复。

验收：历史快照重存、同步后取消收藏、并发移除、收藏已是更高版本四种情况分别验证。

### S5 · P2：非空但损坏的 PDF 仍被视为已同步

位置：`src/arxiv_ra/version_sync.py:176-194`。

首次下载会用 PyMuPDF 校验有效页，但复用仅检查 metadata 身份和文件大小大于零。离线复现：将成功同步的 PDF 改成 7 字节 `bad pdf` 后再次同步，输出 `downloads: 1 status: succeeded size: 7`，未重新下载。这不满足架构说明中的 validated PDFs，也影响随后生成报告和导出附件。

建议：保存下载文件摘要和大小，复用时校验；不匹配时重新验证 PDF 或重新下载。修复仍应先写临时文件、验证成功后发布，避免破坏最后可用文件。

验收：空文件、非空损坏、文件被替换、metadata/PDF 不匹配；有效缓存不产生重复下载。

### S6 · P3：版本编排器直接处理 Zotero 私有协议

位置：`src/arxiv_ra/version_tracker.py:83-97`。

Tracker 调用 `ZoteroClient._get_items()`，自己解析 `archiveID/extra/url`。这违反 README 开发规范及 ARCHITECTURE “外部 API 协议放在适配模块”的明确边界。它不是已观察到的用户数据错误，优先级低于上面问题。

建议：ZoteroClient 暴露返回领域对象的 `list_trackable_papers()`，在适配器内统一分页、ID 解析、来源和失败信息。无需因此重构整个 Tracker。

Standards 共 6 项：5 项正确性/安全风险、1 项明确模块边界问题；最高级别为 S1（P1）。

## Spec：功能承诺与实际行为

### F1 · P1：同日无新推荐时跳过自动周报与版本检查

位置：`src/arxiv_ra/pipeline.py:69-73,95-97`。

当本次筛选无论文且当天已有推荐时，直接返回已有日报，后面的 `_run_optional_integrations()` 不再执行。因此已开启的版本检查、检查后的自动同步、到期周报也被跳过。README 的自动同步说明明确将“每日任务中的版本检查”作为触发入口，这不应依赖当天是否有新的推荐入选。

离线桩验证：有已有推荐、筛选为空时，返回日报路径，后续集成桩调用次数为 0。现有保留旧推荐测试关闭了周报/版本追踪，未覆盖此条件。

建议：推荐发布与后续定时职责分开；保留旧日报的同时，按各自策略运行到期任务，并显示各组件结果。避免为修复此问题而重复发送旧推荐邮件。

验收：同日第二次无新论文、定时任务在手动刷新后运行、周报到期、版本检查失败分别覆盖。

### F2 · P2：空正文仍进入“完整报告”模型流程

位置：`src/arxiv_ra/report.py:229-261`；`src/arxiv_ra/pipeline.py:466`。

报告生成器只检查 `ParsedPaper` 对象是否存在，没有检查正文是否为空白。离线传入 `ParsedPaper('   ', [])`，fake LLM 被调用两次，报告未带抽取回退提示。另一方面，pipeline 的 metadata 会将相同输入标为 `abstract`，造成正文生成路径与质量状态不一致。README 承诺全文解析失败输出带提示的回退结果。

建议：模型调用前校验有效正文；空正文直接使用明确标注的摘要级回退。进一步记录解析页数、字符数、截断信息；“解析器返回对象”不应等于“取得可用全文”。

验收：空字符串、纯空白、扫描 PDF 无文本、部分正文、正常全文；空证据不触发全文模型请求。

### F3 · P2：摘要回退缓存阻止服务恢复后重试（上轮遗留，已复验）

位置：`src/arxiv_ra/abstracts.py:87-96,187-194`。

第一次模型异常时写入 `source=fallback`，以后只核对签名和字段非空便复用，不检查来源；签名也不包含模型配置。离线复验：fake LLM 第一次超时、第二次准备成功，两次执行总调用数仍为 1。启用/修复模型后普通生成可能持续显示回退文字。

建议：区分模型成功、报告抽取、临时错误与未配置模型；回退设置重试策略或显式刷新，成功缓存标记模型/提示词版本。页面 GET 保持不调用模型，刷新应发生在明确生成动作中。

验收：无模型→启用、超时→恢复、模型切换、成功缓存正常复用、页面访问不产生模型调用。

Spec 共 3 项：1 项 P1、2 项 P2；最高级别为 F1（自动检查与周报被跳过）。

## 结构与性能建议

- **统一操作对象。** 沿用现有精确报告选择和快照机制，给页面操作一个明确的论文引用，包含方向、基础 ID、修订版和来源记录。收藏、报告、Zotero 不应各自重新猜测对象。
- **把步骤成功与当前状态有效分开。** 同步步骤保存的成功是历史事实；复用还需检查当前文件、阅读状态和外部目标。对于报告模型配置变化，应明确“复用”还是“重建”的产品语义，再决定有效性签名。
- **逐步建立本地产物索引。** `report_library()`、`matching_report()` 多次遍历所有报告；摘要和周报对每篇论文重复扫描。先在一次请求/任务中复用目录快照，再按规模考虑 SQLite/FTS 索引，文件继续作为成果来源。本次未做规模基准，不把静态复杂度直接当成已发生的性能故障。
- **保留编排与适配器边界。** 优先抽取稳定领域操作，避免把 `web.py` 行数多直接等同于需要重写；先处理 S6 这种可定位的职责泄漏。
- **增加生成质量评估样本。** 在现有离线单测之外，准备覆盖短文、长文、扫描 PDF、复杂公式、表格和多修订版的样本；衡量证据覆盖、数值忠实度、推荐相关性、耗时和成本。真实模型评估应单独记录使用的模型与配置。

## 建议实施次序

1. **可信与正确性**：报告净化、页面方向/快照绑定、空正文降级、回退缓存可恢复。
2. **自动运行与恢复**：解耦无新推荐路径的定时职责，同步复用时检查收藏/PDF真实状态，补充对应离线回归。
3. **研究积累**：阅读进度、个人笔记、质量标签、反馈撤销和活动周报。
4. **研究综合**：全文检索与有证据的跨论文比较，再根据实际使用量完善通用任务恢复、多方向调度和索引。

各轴结果：Standards 6 项（最高 P1：报告同源脚本风险）；Spec 3 项（最高 P1：F1 影响每日自动检查/周报）；功能增强建议 9 项，不与缺陷混算。
